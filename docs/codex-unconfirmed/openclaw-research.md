# Recovering a delivered message's confirmation

Research for [Ovis #2421](https://github.com/devswha/ovis/issues/2421), checked 30 October 2026 against primary documentation and source. OpenClaw source: `0f359b36dc48808097dae18767cf9ccb49390ccb`; acpx source: `6ce38c34f4e5aef16bf28ca8b1fb1e6650695c60` (0.21.1), with the watch contract also verified on release 0.21.0 (`c0b9dfdfad12ed4fc000b8ef2efc4b5644f1c3dc`). No live OpenClaw or Codex run was performed.

## What OpenClaw owns

OpenClaw's current default Codex route is its native Codex app-server integration. Codex through ACP is an explicit alternative using the official `@openclaw/acpx` plugin and `@agentclientprotocol/codex-acp`. The plugin revision inspected pins acpx 0.21.0 and codex-acp 2.2.2. The adapter is a separate Agent Client Protocol project: it starts Codex App Server, translates ACP requests into Codex operations, and translates events back. It is not a way to acknowledge keystrokes sent to an existing Herdr terminal. [OpenClaw routes](https://docs.openclaw.ai/tools/acp-agents), [plugin dependencies](https://github.com/openclaw/openclaw/blob/0f359b36dc48808097dae18767cf9ccb49390ccb/extensions/acpx/package.json), [adapter architecture](https://github.com/agentclientprotocol/codex-acp/blob/ac8d9251de43ab8648a89eb0520e0c606ad78be5/README.md).

The ACP stack separates the OpenClaw session identity, backend session identity, request identity and completion. The harness attempt creates a persistent session, obtains an admitted transcript-entry receipt and creates a request ID from that entry plus a UUID. Assistant persistence gets its own idempotency key derived from that request. The runtime exposes `promptStarted`, events and `result` separately. An acknowledgement that transport accepted a prompt does not mean its model turn completed. [Harness admission and request identity](https://github.com/openclaw/openclaw/blob/0f359b36dc48808097dae18767cf9ccb49390ccb/extensions/acpx/src/harness-attempt.ts#L155), [request creation](https://github.com/openclaw/openclaw/blob/0f359b36dc48808097dae18767cf9ccb49390ccb/extensions/acpx/src/harness-attempt.ts#L255), [runtime result surface](https://github.com/openclaw/openclaw/blob/0f359b36dc48808097dae18767cf9ccb49390ccb/extensions/acpx/src/runtime.ts#L1052).

## How confirmation survives a disconnected reader

ACPx provides passive `sessions watch` for its CLI/shared-session path. Its retained journal associates events with an exact submitting request ID and opaque cursor. A watcher can reconnect from its last cursor and observe `turn_result`, whose status is completed, cancelled or failed. Disconnecting a watcher neither sends the prompt again nor cancels it. `turn_started` means an attempt was selected; `promptStarted` indicates prompt transport acceptance; `turn_result` follows cleanup and checkpoint attempts. If the owner disappeared without recording a result, the observer gets `WATCH_OUTCOME_UNKNOWN`. It must not infer success from partial output. Retention is bounded: expired cursors fail explicitly. Custom in-process stores do not automatically publish this CLI/shared journal. This is an acpx capability; I did not establish that OpenClaw's browser uses this watch API. [Release-pinned watch contract](https://github.com/openclaw/acpx/blob/c0b9dfdfad12ed4fc000b8ef2efc4b5644f1c3dc/docs/session-watch.md), [journal implementation](https://github.com/openclaw/acpx/blob/6ce38c34f4e5aef16bf28ca8b1fb1e6650695c60/src/session/events.ts#L222).

OpenClaw's browser has a separate recovery mechanism. Its queued send retains the original request/idempotency key and physical conversation identity through reconnect. Tests explicitly cover reconnecting after a written frame lost its reply. Gateway admission checks the exact previous request and returns cached or in-flight state; the comparison reads the submitted message by its request-derived identity under the session/lifecycle scope and rejects conflicting input. This is stronger than matching a visible string. [Browser reconnect tests](https://github.com/openclaw/openclaw/blob/0f359b36dc48808097dae18767cf9ccb49390ccb/ui/src/pages/chat/chat-outbox-reconnect.test.ts), [written-frame recovery](https://github.com/openclaw/openclaw/blob/0f359b36dc48808097dae18767cf9ccb49390ccb/ui/src/pages/chat/chat-outbox-transient-recovery.test.ts#L170), [cached admission](https://github.com/openclaw/openclaw/blob/0f359b36dc48808097dae18767cf9ccb49390ccb/src/gateway/server-methods/chat-send-pre-admission.ts#L164), [exact request comparison](https://github.com/openclaw/openclaw/blob/0f359b36dc48808097dae18767cf9ccb49390ccb/src/gateway/server-methods/chat-send-retry-comparison.ts#L39).

Its pending-input UI queries exact run IDs and reconciles pending/consumed/cancelled custody receipts. A receipt or an explicitly queried absence can retire that specific projection; an unrelated empty history page cannot settle arbitrary saved input. The UI also checks the physical session before removing a browser queue copy. [Pending-input reconciliation](https://github.com/openclaw/openclaw/blob/0f359b36dc48808097dae18767cf9ccb49390ccb/ui/src/pages/chat/chat-pending-inputs.ts#L36), [settling queue copies](https://github.com/openclaw/openclaw/blob/0f359b36dc48808097dae18767cf9ccb49390ccb/ui/src/pages/chat/chat-pending-inputs.ts#L218).

Cancellation is explicit. ACPx requests cooperative session cancellation and waits briefly for a cancelled result before forced cleanup. Watching/disconnecting alone is observation. OpenClaw separately stops automatic ingress startup retries once a prepared ACP turn is accepted, so a slow answer is not a reason to dispatch the trigger again. [ACPx cancellation](https://github.com/openclaw/acpx/blob/c0b9dfdfad12ed4fc000b8ef2efc4b5644f1c3dc/docs/sessions.md#cancelling), [OpenClaw delivery rules](https://github.com/openclaw/openclaw/blob/0f359b36dc48808097dae18767cf9ccb49390ccb/docs/tools/acp-agents/delivery.md#delivery-model).

## Applying the lesson to Ovis

The transferable mechanism is exact, server-owned outcome recovery. ACP itself is not required. Ovis already has a PTY send boundary and a browser/device receipt-resume identity for Pi. Extend the presentation recovery pattern rather than replacing how a terminal receives prompts.

Proposed bounded change, inferred from those sources and Ovis's reproduced failure:

1. Retain each ordinary pending message's terminal disposition under its exact message ID, pane and authenticated browser/device resume owner. Record it before trying to notify the socket. Retain no execution authority.
2. On reattach by that same owner, replay successful/withdrawn dispositions through the existing pending-message protocol. Let an exact receipt settle the corresponding recovery copy even though its old connection scope is gone.
3. Reconnecting performs no paste, Enter or prompt resubmission. Do not copy OpenClaw's automatic `chat.send` retry into Ovis: its send contract differs.
4. An expired, missing or unprovable receipt leaves the saved row uncertain. Text equality, agent completion and an empty snapshot are not delivery receipts. Preserve Herdr lifetime fencing and owner isolation.

Tests should lose the successful removal receipt, reconnect and reload, then prove the exact row disappears and terminal bytes remain a single delivery. Also cover a different resume owner/device, two same-text sends with different IDs, no receipt, retention expiry, live ownership on another connection, a replaced Herdr lifetime, duplicate receipts, and a failure after paste but before committed Enter. A before/after screenshot should use the same fictional transcript and fault boundary.

This repairs one proven trigger of #2421. It does not establish why the original browser lost confirmation, provide exactly-once execution across bridge restarts, or prove that a PTY Enter is a native Codex model-acceptance acknowledgement.
